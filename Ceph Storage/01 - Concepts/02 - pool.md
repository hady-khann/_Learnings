# Pool چیست؟

**Pool** یک فضای منطقی برای ذخیره‌سازی داده‌هاست که مجموعه‌ای از سیاست‌ها و تنظیمات مشخص روی آن اعمال می‌شود.

هر Pool می‌تواند مشخص کند:

* چند Replica از داده نگه داشته شود؛ مثلاً `size=3`
* داده روی چه دسته‌ای از OSDها قرار بگیرد؛ مثلاً SSD
* از **Replication** یا **Erasure Coding** استفاده شود.
* چه تعداد **PG** داشته باشد.
* از چه CRUSH Ruleای استفاده کند.

### مثال

یک Pool می‌تواند برای دیتابیس باشد:

```text
SSD + replica=3 + عملکرد بالا
```

و Pool دیگری برای آرشیو:

```text
HDD + replica=2 + هزینه کمتر
```

---

# PG — Placement Group

PG یک لایه‌ی میانی بین **Objectها** و **OSDها** است.

به‌جای اینکه Ceph برای میلیون‌ها یا میلیاردها Object به‌صورت جداگانه مکان‌یابی و مدیریت انجام دهد، Objectها ابتدا به PGها تعلق می‌گیرند و سپس CRUSH مشخص می‌کند PG روی کدام OSDها قرار بگیرد.

```text
Objectها
   ↓
Hash
   ↓
PG
   ↓
CRUSH
   ↓
OSD
```

## چرا PG لازم است؟

بدون PG، مدیریت مکان میلیون‌ها Object بسیار سنگین می‌شد.

PG باعث می‌شود:

* مدیریت داده مقیاس‌پذیرتر شود.
* Recovery به‌صورت موازی انجام شود.
* توزیع داده بین OSDها بهتر انجام شود.
* تغییرات کلاستر ساده‌تر مدیریت شوند.

---

## Replica در سطح PG

نکته‌ی بسیار مهم:

**Replica به‌صورت مستقل برای هر Object انتخاب نمی‌شود؛ Object از PG خود پیروی می‌کند.**

هر PG یک **Acting Set** دارد؛ مثلاً:

```text
PG.100
  ├── OSD.1
  ├── OSD.7
  └── OSD.12
```

اگر Pool دارای `size=3` باشد، Objectهای متعلق به این PG نیز روی همین Acting Set قرار می‌گیرند.

بنابراین:

```text
Object
  ↓
PG
  ↓
Acting Set
  ↓
OSDها
```

این مدل باعث می‌شود عملیات Write، Recovery و توزیع داده قابل مدیریت و مقیاس‌پذیر باشند.

---

# رابطه‌ی Pool، PG و OSD

```text
Pool
 └── PG
      └── OSD
```

* **Pool** = سیاست و فضای منطقی
* **PG** = واحد میانی مدیریت و توزیع
* **OSD** = محل فیزیکی ذخیره‌سازی

---

# محاسبه‌ی تعداد PG

یک تقریب کلاسیک برای محاسبه‌ی PG:

```text
Total PGs ≈ (OSD Count × Target PGs per OSD) / Replica Size
```

اما در محیط‌های دارای چند Pool، محاسبه باید **سهم هر Pool از داده** را نیز در نظر بگیرد.

برای همین، در محیط‌های مدرن Ceph بهتر است به‌جای محاسبه‌ی دستی، از **pg_autoscaler** استفاده شود.

---

# PG و تعداد OSD

عددهایی مانند ۱۰۰ تا ۲۰۰ PG به ازای هر OSD را نباید به‌عنوان یک قانون مطلق در نظر گرفت.

هدف این است که تعداد PGها:

* بیش از حد کم نباشد تا توزیع داده ضعیف نشود.
* بیش از حد زیاد نباشد تا مصرف CPU و RAM و هزینه‌ی Recovery افزایش پیدا نکند.

همچنین اگر تعداد OSD تقریباً برابر Replica باشد، آزادی CRUSH برای توزیع داده بسیار محدود می‌شود.

مثلاً:

```text
5 OSD
replica = 5
```

در این حالت هر PG عملاً مجبور است روی هر ۵ OSD قرار بگیرد.

---

# تغییر تعداد OSD

با اضافه یا حذف OSD، توزیع PGها نیز ممکن است تغییر کند.

Ceph می‌تواند PGها را Split یا Merge کند و داده‌ها را مجدداً توزیع کند.

این عملیات بدون تعویض فیزیکی دیسک‌ها انجام می‌شود، اما می‌تواند باعث:

* جابه‌جایی داده
* مصرف شبکه
* مصرف دیسک
* افزایش CPU/IO
* افزایش Recovery Load

شود.

به همین دلیل در کلاسترهای واقعی استفاده از **pg_autoscaler** اهمیت زیادی دارد.

---

# آیا یک OSD می‌تواند عضو چند Pool باشد؟

بله.

یک OSD می‌تواند هم‌زمان PGهایی از چند Pool مختلف را نگه دارد:

```text
OSD.5
 ├── PG از Pool: fast-db
 ├── PG از Pool: vm-disks
 └── PG از Pool: backup
```

Pool یک تقسیم‌بندی فیزیکی دیسک نیست؛ یک **لایه‌ی منطقی و سیاست ذخیره‌سازی** است.

مثلاً اگر چند Pool از OSDهای دارای `class=ssd` استفاده کنند، همه‌ی آن Poolها می‌توانند روی همان مجموعه‌ی SSDها قرار بگیرند.

---

# محدودیت واقعی

محدودیت اصلی، ظرفیت و منابع فیزیکی OSD است.

اگر چند Pool از یک مجموعه OSD استفاده کنند، مصرف مجموع آن‌ها باید در ظرفیت و توان عملیاتی OSDها جا شود.

برای بررسی وضعیت:

```bash
ceph osd df
```

و برای بررسی سلامت کلاستر:

```bash
ceph health detail
```

---

# Best Practice برای چند Pool

اگر یک OSD در Poolهای زیادی استفاده شود، PGهای تمام Poolها روی همان OSD جمع می‌شوند.

بنابراین:

> معیار PG، **مجموع PGهای تمام Poolها روی OSD** است، نه PG هر Pool به‌صورت جداگانه.

به همین دلیل:

1. PG هر Pool را بر اساس حجم و اهمیت واقعی آن تعیین کن.
2. Poolهای کوچک را با PG بیش از نیاز ایجاد نکن.
3. از `pg_autoscaler` استفاده کن.
4. وضعیت `ceph health detail` را بررسی کن.
5. تعداد PG را صرفاً برای رسیدن به یک عدد ثابت روی هر Pool افزایش نده.

---

## pg_autoscaler

برای فعال‌سازی روی یک Pool:

```bash
ceph osd pool set mypool pg_autoscale_mode on
```

در محیط‌های دارای Poolهای متعدد، این روش معمولاً از محاسبه‌ی دستی قابل اتکاتر است.

## نکته‌ی مهم درباره‌ی PGCalc

ابزارهای محاسبه‌ی PG می‌توانند برای طراحی اولیه مفید باشند، اما در یک کلاستر واقعی باید علاوه بر تعداد OSD و Replica، مواردی مانند:

* حجم واقعی داده
* رشد آینده
* نوع Pool
* CRUSH Rule
* Failure Domain
* تعداد Poolها
* محدودیت منابع

را نیز در نظر گرفت.

**PG بیشتر لزوماً بهتر نیست.**
