# Placement Groups و PG Autoscaler

## `pg_num`

تعداد Placement Groupهای Pool را مشخص می‌کند.

PGها نقش مهمی در نحوه توزیع داده روی OSDها دارند و انتخاب نامناسب تعداد PG می‌تواند روی توزیع بار و عملکرد کلاستر تأثیر بگذارد.

مثال:

```yaml
pg_num: 16
```

در یک کلاستر کوچک آموزشی، مقادیر محدودی مانند:

```yaml
pg_num: 8
```

یا:

```yaml
pg_num: 16
```

یا:

```yaml
pg_num: 32
```

ممکن است مناسب باشند؛ اما مقدار صحیح به تعداد OSDها، تعداد Poolها، ظرفیت و Workload واقعی بستگی دارد.

> در Cephهای جدید، قبل از محاسبه دستی PG، وضعیت PG Autoscaler را بررسی کنید.

---

## `pgp_num`

تعداد PGهایی را مشخص می‌کند که برای Placement استفاده می‌شوند.

در تنظیمات معمول:

```yaml
pg_num: 16
pgp_num: 16
```

یعنی هر دو مقدار برابر هستند.

در بیشتر سناریوهای عادی نیازی به متفاوت بودن این دو مقدار وجود ندارد.

> اگر دقیقاً نمی‌دانید چرا `pg_num` و `pgp_num` باید متفاوت باشند، آن‌ها را متفاوت تنظیم نکنید.

---

# PG Autoscaler

## `pg_autoscale_mode`

نحوه مدیریت تعداد PGها توسط Ceph را مشخص می‌کند.

سه حالت اصلی:

```text
on
warn
off
```

---

## `on`

Ceph تعداد PGها را بر اساس وضعیت Pool و مصرف Storage مدیریت می‌کند.

```yaml
pg_autoscale_mode: on
```

مزیت اصلی:

* نیاز کمتر به محاسبه دستی PG
* مناسب‌تر برای کلاسترهایی که Poolها در طول زمان رشد می‌کنند

برای محیط آموزشی معمولاً گزینه راحت‌تری است.

---

## `warn`

Ceph فقط در صورت نامناسب بودن تعداد PG هشدار می‌دهد.

```yaml
pg_autoscale_mode: warn
```

در این حالت تغییر PG به‌صورت خودکار انجام نمی‌شود.

---

## `off`

مدیریت PG کاملاً دستی است.

```yaml
pg_autoscale_mode: off
```

در این حالت مسئولیت انتخاب و تغییر `pg_num` با Administrator است.

---

# `target_size_ratio`

به PG Autoscaler یک تخمین از سهم مورد انتظار Pool از ظرفیت کل کلاستر می‌دهد.

مثال:

```yaml
target_size_ratio: 0.2
```

یعنی انتظار دارید این Pool در نهایت تقریباً 20٪ از ظرفیت موردنظر کلاستر را مصرف کند.

مقادیر نمونه:

```text
0.2 = 20%
0.5 = 50%
1.0 = 100%
```

این مقدار یک **Hint** است، نه Hard Limit.

---

## چرا `target_size_ratio` مهم است؟

یک Pool تازه‌ساخته‌شده ممکن است هنوز داده زیادی نداشته باشد.

در چنین شرایطی Autoscaler بر اساس مصرف فعلی اطلاعات محدودی برای تخمین اندازه آینده Pool دارد.

مثلاً اگر انتظار دارید:

```text
mypool       → 50%
archive      → 30%
logs         → 10%
```

می‌توانید نسبت‌های تقریبی را مشخص کنید:

```yaml
mypool:
  target_size_ratio: 0.5

archive:
  target_size_ratio: 0.3

logs:
  target_size_ratio: 0.1
```

مجموع دقیقاً لازم نیست 1.0 باشد؛ مهم این است که نسبت‌ها با طراحی واقعی Storage همخوانی داشته باشند.

---

## بررسی وضعیت Autoscaler

دستور اصلی:

```bash
ceph osd pool autoscale-status
```

این دستور اطلاعاتی مانند موارد زیر را نشان می‌دهد:

```text
POOL
SIZE
TARGET SIZE
RATIO
TARGET RATIO
PG_NUM
NEW PG_NUM
AUTOSCALE
```

مهم‌ترین ستون‌ها:

### `SIZE`

مقدار فعلی داده Pool.

### `RATIO`

سهم فعلی Pool نسبت به ظرفیت Storage.

### `TARGET RATIO`

مقداری که از طریق `target_size_ratio` تعیین شده است.

### `PG_NUM`

تعداد PG فعلی Pool.

### `NEW PG_NUM`

مقداری که Autoscaler پیشنهاد می‌کند.

اگر این مقدار نمایش داده شود، یعنی Autoscaler تغییر PG را پیشنهاد کرده یا در حال اعمال آن است.

### `AUTOSCALE`

حالت فعلی Autoscaler:

```text
on
warn
off
```

---

## یک نکته مهم درباره تغییرات PG

اگر `NEW PG_NUM` مرتب تغییر می‌کند، معمولاً یکی از این موارد در حال رخ دادن است:

1. Pool هنوز در حال رشد است.
2. مصرف Storage هنوز پایدار نشده است.
3. `target_size_ratio` با مصرف واقعی Pool مطابقت ندارد.
4. وضعیت کلی Poolها در حال تغییر است.

بنابراین صرفاً دیدن یک مقدار `NEW PG_NUM` به معنی مشکل نیست.

بهتر است وضعیت را در طول زمان بررسی کنید:

```bash
ceph osd pool autoscale-status
```

و بعد از تغییرات مهم دوباره آن را بررسی کنید.

---

## نکته عملی

برای یک محیط کوچک آموزشی، این رویکرد معمولاً ساده‌تر است:

```yaml
pool_type: replicated
pg_autoscale_mode: on
```

و در صورت نیاز:

```yaml
target_size_ratio: 0.2
```

در Production، تنظیم PG باید بر اساس ظرفیت واقعی، تعداد OSDها، تعداد Poolها، نوع Workload و Failure Domain طراحی شود؛ نه صرفاً با یک مقدار ثابت مانند `32`.
